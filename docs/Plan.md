# Execution Plan for BhoomiSetu Implementation

## Context
BhoomiSetu is a GIS-based, parcel-centric land governance and interoperability platform designed to connect fragmented land-related datasets through a unified digital framework. The prototype demonstrates a practical implementation aligned with the Land Stack vision, addressing the challenge of accessing complete parcel-level information across multiple government departments. This plan outlines the execution steps to build a functional prototype based on the technical documentation provided in BHOOMISETU.md and Tech.md.

## Current Status
We have:
- Created the complete project structure for both backend and frontend
- Implemented core GIS functionality with proper spatial endpoint fallbacks
- Configured TypeScript with proper decorator settings
- Created a seed script for generating mock data
- Encountered and resolved a TypeORM decorator compilation issue by using the correct tsconfig settings

## Recommended Approach
Follow the MVP priority outlined in Section 47 of Tech.md, implementing phases sequentially to ensure a solid foundation before adding complexity. The approach emphasizes building the GIS foundation first, then parcel core, mock department APIs, interoperability layer, and finally citizen/officer portals with AI and security layers.

**Addendum (2026-09-04) — connected cluster topology + explicit neighbour relationships**: The previous addendum's parcels were geographically clustered but each polygon was still generated independently (star-shaped around its own jittered center) — neighbouring parcels sat close with a gap, never sharing an actual boundary, and `/neighbours` classified TOUCHING/NEARBY by computing live geometry distance on every request. Both are replaced with a proper shared topology:

- **`Parcel.clusterId`** (nullable, indexed) identifies the connected network a parcel belongs to (`MH-PUNE-01`, `TN-CHENNAI-01`, `KA-BANGALORE-01`, `DL-NEWDELHI-01`).
- **`backend/seed.ts` geometry generation was replaced with a shared-vertex lattice** (`buildLattice`/`buildEdgeMidpoints`/`parcelRing` in seed.ts): a `(rows+1)×(cols+1)` grid of corner points is jittered *once* per cluster, and each shared edge gets one jittered midpoint, both looked up (not regenerated) by every parcel touching that corner/edge — so two parcels sharing a boundary use the *literal same coordinates* for it by construction, not by getting lucky with proximity. Verified directly against the live API: fetching a parcel and its `TOUCHING` neighbour, 3–4 coordinates are byte-identical between the two polygons' rings. Each parcel is now an 8-vertex ring (corner, edge-midpoint, corner, ...) — irregular, but never gapped or overlapping.
- **New `ParcelNeighbour` entity** (`parcel_neighbours`: `id`, `parcelId`, `neighbourParcelId`, `relationshipType`) stores explicit relationships generated at seed time from known grid row/column position (not recomputed from geometry): the 4 orthogonal grid neighbours are `TOUCHING`, the 4 diagonal ones are `NEARBY`, inserted bidirectionally by iterating every cell's full 8-neighbourhood. Seeding produced exactly 1286 rows across all 4 clusters, matching the interior/edge/corner cell-count math exactly. `ParcelsService.getNeighbours` now reads this table first and only falls back to the old live-distance calculation when a parcel has no rows (e.g. hand-built test fixtures) — verified with a dedicated test using two geometrically-*far-apart* parcels linked explicitly as TOUCHING plus a geometrically-*close* unlinked third parcel, proving the table (not proximity) drives the result once rows exist.
- **New `GET /api/v1/parcels/:parcelId/context`** returns `selectedParcel` + `cluster: {clusterId}` + `clusterParcels` (every parcel sharing that clusterId, not just neighbours) + `adjacentParcels`/`nearbyParcels` (delegates to `getNeighbours`). Falls back to a single-parcel "cluster" for non-clustered data.
- **`MapComponent`** gained a `cluster-layer` (gray-slate fill, default **on** — unlike same-district/overlay layers, a selected parcel's cluster must never be hidden by default) fed by `clusterParcels`, and the buffered-zoom `fitBounds` now targets the *whole cluster's* combined bounds instead of just selected+adjacent+nearby, per the "fit to ALL CLUSTER PARCEL BOUNDS, not selected parcel bounds" requirement. `Parcel360View` picks this up for free since it already renders `MapComponent`.

Verified visually in a headless browser: selecting a Pune parcel now shows the entire 100-parcel cluster as a filled region across the whole viewport (buffer-zoomed to it), with the selected parcel (blue), its 2 touching neighbours (orange), and a diagonal nearby parcel (thin outline) all visible together inside it — a direct visual match to the spec's connected-web diagram. Added 7 new backend e2e tests (43 total: precomputed-relationship-priority test, 6 `/context` tests) and updated `MapComponent.test.tsx`'s fixtures to a 4-parcel cluster including one parcel that's in the cluster but neither adjacent nor nearby, to prove the cluster layer shows the *whole* network and `fitBounds` receives its full extent (17 frontend tests, unchanged count — fixtures grew, test count didn't). `tsc --noEmit`, both test suites, and the production build are clean on both sides.

Chose Node/TypeScript - no new runtime to install/deploy/document, and `docker-compose.yml`'s existing scaffold already treats every other "service" (including the AI service) as the same NestJS backend under an env var, not a genuinely separate codebase.

- **`backend/src/change-detection/image-diff.ts`** - pure, dependency-free functions implementing Tech.md #33's CHANGE ANALYSIS/CHANGE REGION steps by hand (matching this codebase's existing preference - see `common/geo-utils.ts` - for writing the actual algorithm instead of pulling in a library): `diffImages()` compares two same-sized raw RGBA buffers pixel-by-pixel (average per-channel absolute difference above a threshold = "changed"), returns the bounding box of changed pixels plus a changed-pixel ratio, and treats anything below 0.2% of the image as noise rather than a real change. `pixelBoxToGeoBox()` maps that pixel bounding box back into a real geographic rectangle using the caller-supplied bounds the two images cover.
- **`ChangeDetectionService.analyze()`** - `sharp` decodes/resizes both uploaded images (any common format) to a fixed 200x200 analysis grid, runs the diff, and if a real change was found: builds the GeoJSON change region, then does the actual **SPATIAL INTERSECTION** - every parcel's centroid tested against the change region with `geo-utils.ts`'s real `pointInRing` (not hand-picked, not PostGIS in dev for the same reason nothing else in this codebase is, but ready to swap for `ST_Intersects`), then creates a real `ChangeDetectionEvent` row (Phase 2's entity, previously only ever seed-time data) and one real `GovernanceAlert` per affected parcel (Phase 7's entity/table, `UNAUTHORIZED_CHANGE_DETECTED`/`CHANGE_DETECTION`, same convention the seeded alerts already use - severity HIGH above a 5% change ratio, MEDIUM below).
- **`POST /api/v1/change-detection/analyze`** (`ChangeDetectionController`) - multipart fields `before`/`after` (images, 5MB cap each) plus `minLng`/`minLat`/`maxLng`/`maxLat`/optional `description` in the body. 400 for a missing file, a non-image file, or out-of-range coordinates.
- **Frontend** (not in Plan.md's own checklist for this phase, same as Phase 4/8 - added after asking, matching the pattern set in Phase 8): `ChangeDetectionPanel` in the Officer Portal - file pickers for both images, a bounds form (with a "Use Pune cluster bounds" one-click fill against the real seeded cluster), and a result view listing affected parcels with links into Parcel 360.
